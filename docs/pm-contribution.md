# Play Pick 온보딩 기여와 근거

## 첫 추천까지의 흐름

PlayPick은 회원가입 직후 공연 카드를 한 장씩 보여 주고, 첫 추천에 사용할 취향 신호를 수집합니다. 사용자는 `보고싶어요`, `모르겠어요`, `안볼래요` 중 하나로 응답합니다. 세 응답의 처리 방식은 현재 `release` 코드에서 다음과 같이 구분됩니다.

- **`보고싶어요`**: 프론트엔드의 `likes`에 기록하고 완료 개수에 포함합니다. 서버에는 `1.5`로 저장하며 벡터 계산에 사용합니다.
- **`안볼래요`**: `dislikes`에 기록하고 완료 개수에 포함합니다. 서버에는 `-1.0`으로 저장하며 벡터 계산에 사용합니다.
- **`모르겠어요`**: `skips`에만 기록합니다. 완료 개수에서 제외하고 서버에 전송하지 않으므로 벡터 계산에도 들어가지 않습니다.

따라서 명세에 적힌 `모르겠어요: 0`은 응답의 의미를 설명하는 값입니다. 현재 구현은 0 신호를 서버에 저장하거나 벡터 합산에 넣지 않습니다. 관심과 비선호의 합계가 8개 이상일 때만 완료할 수 있습니다.

완료 버튼을 누르면 프론트엔드는 관심·비선호를 API 형식으로 변환한 뒤 신호 저장 요청을 먼저 보냅니다. 저장이 성공해야 완료 요청을 이어서 보내며, 두 요청까지 성공해야 화면 상태를 `completed`로 바꿉니다. 저장 또는 완료 요청이 실패하면 오류 메시지를 남기고 성공 화면으로 이동하지 않습니다. 두 요청은 별도 API이므로 저장 성공 뒤 완료 요청만 실패한 경우에는 앞서 저장된 신호가 서버에 남을 수 있습니다.

## 개인과 팀의 기여 범위

- **이재호**: 온보딩 화면·Pinia 상태·API 연결과 서버의 신호 저장·완료 흐름을 처음 연결했습니다. 관람함과 마이페이지 연동, 관련 명세도 [`6fde165` 최초 구현 커밋](https://github.com/Play-Pick/playpick/commit/6fde1652b2ef6cdfb0259568c27d3892e7d443f4)에 포함됩니다.
- **임경수**: [팀 역할](../README.md#역할과-확인된-결과)에 기록된 KOPIS 데이터 수집, Django API, AI 검색·핵심 추천 시스템, 배포와 프론트엔드 리팩터링을 담당했습니다. 온보딩 코드에도 [`21d7fb1` 구조 개선](https://github.com/Play-Pick/playpick/commit/21d7fb12327df5bea20948bbc24b914d15eec822)과 [`336e415` 개수 로직 수정](https://github.com/Play-Pick/playpick/commit/336e415f9d32886dc8c412fb2c5306c8c0ff7335)이 반영돼 있습니다.
- **팀 결과**: 현재 `release`는 최초 구현 이후의 리팩터링과 수정이 합쳐진 결과입니다. [현재 추천 엔진](../back/recommendations/services/engine.py)의 가중치와 내부 점수는 서비스 구현값이며, 추천 정확도나 사용자 만족도 성과가 아닙니다. [추천 설계](../README.md#추천과-검색-설계)에서 각 신호의 구현 기준을 확인할 수 있습니다.

최초 구현 커밋은 프론트엔드와 온보딩 서버 코드를 함께 포함하지만, 이것이 현재 백엔드·추천 시스템 전체를 개인이 단독 구현했다는 뜻은 아닙니다. 현재 공개 코드의 모듈 구조와 세부 동작에는 이후 팀원의 변경이 반영돼 있습니다.

## 현재 동작을 확인하는 코드

- [온보딩 상태와 제출 순서](../front/src/stores/onboardingStore.js): 관심·비선호 합계, 8개 완료 조건, 중립 제외, 저장 후 완료 요청, 실패 상태를 확인할 수 있습니다.
- [온보딩 화면](../front/src/views/Auth/OnboardingView.vue): 세 응답 버튼, 완료 버튼 비활성화, 오류 표시와 성공 후 이동 조건을 확인할 수 있습니다.
- [프론트엔드 API](../front/src/api/onboarding.js): 후보 조회, 신호 저장, 완료 요청이 서로 다른 API 호출임을 확인할 수 있습니다.
- [신호 저장과 벡터 계산](../back/accounts/services/onboarding_service.py): 신호 저장, 공연 임베딩의 가중 합산, L2 정규화와 완료 상태 갱신을 확인할 수 있습니다.
- [온보딩 API](../back/accounts/views/onboarding_views.py): 저장 요청과 완료 요청 각각의 8개 검증 및 트랜잭션 범위를 확인할 수 있습니다.
- [당시 기능 명세](final-submission/03-기능-명세/01-온보딩시스템.md): 3단계 응답과 8개 기준, 벡터 계산 목표를 확인할 수 있습니다. 화면 구성 일부는 현재 코드와 다르므로 구현 설명은 위 현재 코드를 우선합니다.

## 확인된 결과와 한계

공개 코드에서는 관심·비선호 8개 이상이라는 완료 조건과 신호 저장 → 완료 요청 순서를 확인했습니다. 2026-09-11에는 별도 로컬 환경과 예시 계정으로 이 흐름을 다시 실행해 중립이 완료 개수를 늘리지 않는 점, 호불호 신호 8개 저장, 1536차원 벡터 생성을 확인했습니다. 이는 원 프로젝트 시점의 사용자 검증이 아니라 이후의 기능 재현이며, [포트폴리오 사례](https://ficstory.dev/pm/play-pick/)에서도 이 범위를 구분해 설명합니다.

실제 사용자의 온보딩 완료율, 추천 정확도, 추천 만족도는 측정 자료를 확인하지 못했습니다. 또한 로컬 재현은 온보딩과 첫 추천 연결만 다뤘으며, 지도·YouTube·자연어 검색 등 다른 외부 연동의 정상 동작을 검증한 결과가 아닙니다.
