## 1. 데이터 모델링 논의

이번 프로젝트의 출발점은 KOPIS 공연 데이터를 우리 서비스의 도메인 모델로 어떻게 변환할 것인가였다. 단순히 API 필드를 그대로 사용하는 것이 아니라, 공연 추천이라는 서비스 목적에 맞게 구조를 재설계해야 했다.

### 주요 고려사항
- 핵심 엔티티 선정
- KOPIS 필드 중 핵심 데이터 선별
- 추천 알고리즘을 위한 관계 설계

### 배운 점
단순한 필드 나열이 아닌, **서비스 흐름을 역추적하여 모델링**해야 한다는 점을 깨달았다. 특히 추천 로직에 필요한 정보(선호 장르, 클릭 로그 등)를 초기 설계 단계에서 충분히 고려하는 것이 중요했다.

## 2. 제약 조건과 우선순위 설정

**프로젝트 조건**
- 기간: 3주
- 팀원: 2명
- 범위: 웹서비스 + 추천 알고리즘

### 초기 고민
- 계획한 기능을 모두 구현할 수 있을까?
- 추천 알고리즘을 어느 수준까지 구현해야 의미 있는 추천이 될까?
- 설계와 구현의 일관성을 어떻게 유지할까?

### 해결 방향
WBS 작성을 통해 핵심 원칙을 도출했다:

> **"모든 걸 완벽히 하려 하면 아무것도 끝내지 못한다. 핵심 흐름에 집중하자."**

**MVP 정의**
- 핵심 경험: 가입 → 선호 설정 → 추천 → 상세 보기
- 부가 기능: 최소화

## 3. WBS와 Gantt 차트 경험

처음으로 WBS와 Gantt 차트를 구글 시트로 작성했다. 단순한 기능 나열과 **"언제 / 누가 / 어느 기간"**까지 구체화하는 것은 완전히 다른 경험이었다.

### 얻은 효과
1. **구체적인 일정 감각**: 막연한 3주가 아닌 하루 단위 태스크로 현실적인 계획 수립
2. **병렬 작업 가시화**: 백엔드 모델링 vs 프론트 화면 구조 등 동시 진행 가능 작업 파악
3. **리스크 조기 발견**: 예상보다 오래 걸릴 작업을 사전에 식별

### 인사이트
Gantt 차트는 단순한 일정표가 아닌 **팀의 개발 전략을 시각화하는 도구**였다. 프로젝트 구조와 우선순위를 정리하는 데 매우 효과적이었다.

## 4. 명세서 구체화의 균형점 찾기

### 딜레마
- 너무 추상적: "공연 추천 기능 구현" → 실행 불가
- 너무 구체적: 모든 라이브러리, 알고리즘, API까지 사전 확정 → 비현실적

### 해결 원칙
> **"현재까지 확실한 것"을 최대한 구체적으로 작성하자**

**명세서 작성 기준**
- 어떤 화면에서
- 어떤 API를 호출하고
- 어떤 데이터 구조를 주고받는지

명세서는 팀의 **공통 이해를 맞추는 기준점**이다. 나중에 수정되더라도 초기 합의점으로서 의미가 있다.

### 향후 목표
기능 명세 시 **"입력 → 처리 → 출력"** 흐름을 명확히 하여 바로 이슈로 전환 가능한 수준으로 작성한다.

## 5. 핵심 인사이트

### 배운 점
1. **기획은 투자다**: 초기 고민이 개발 난이도를 낮춘다
2. **모델링은 설계다**: API 필드 복사가 아닌 서비스 흐름과 추천 로직을 담는 설계 작업
3. **시각화는 강력하다**: WBS와 Gantt 차트를 통한 작업 시각화가 팀 방향성 정렬에 효과적
4. **명세는 자기 질문이다**: 구체화 과정에서 서비스 본질에 대한 깊은 사고 필요

### 다짐
거대한 목표보다 **3주 안에 완성 가능한 핵심 경험(유스케이스)**에 집중하여 기획과 구현을 설계한다.
